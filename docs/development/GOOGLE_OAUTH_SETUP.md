# Google OAuth setup for Routiqo

The login UI/proxy is implemented, but no real OAuth client is configured. Google client IDs are public identifiers; client secrets must never be put in browser/mobile code or task messages. No client secret is required by this Google Identity Services ID-token flow.

## Google project configuration
1. In your Google Cloud project, configure the OAuth consent/branding screen for Routiqo and required contact details. While the app is in testing, add the Google accounts that should test it.
2. Create an OAuth client of type Web application.
3. Add the exact authorized JavaScript origins used by the web app. For local testing use http://localhost:3000 (and http://localhost when required by Google's local setup guidance). Use the same hostname consistently; the preview URL 127.0.0.1 is a different origin.
4. For production add the real HTTPS origin. This implementation uses Google's JavaScript popup callback, not a server redirect callback; do not invent a redirect path.
5. Copy the public client ID ending in .apps.googleusercontent.com. Google registration, consent and actual sign-in must be verified with your configured account; no fake account is supplied by Routiqo.

## Web server environment
Supply server-side environment values before starting Next:
- ROUTIQO_GOOGLE_CLIENT_ID: the Web client ID above
- ROUTIQO_AUTH_API_URL: core API origin, such as http://127.0.0.1:8080 for local development
- ROUTIQO_WEB_ORIGIN: exact browser origin, such as http://localhost:3000

Missing configuration keeps Profile in local-preview mode and does not load Google's script. Restart Next after changing environment variables. Only the public client ID and enabled state are returned to the browser; API origin/secrets remain server-side.

## Core API environment
Use persistence,google-auth,web-auth profiles and the same Google client ID and browser origin. Supply database credentials and a randomly generated shared ROUTIQO_AUTH_RATE_SECRET. Local HTTP requires ROUTIQO_AUTH_SECURE_COOKIES=false; production defaults to Secure cookies and requires HTTPS. See LOCAL_SETUP.md. Migrations apply to the chosen database when this profile starts, so verify its URL first.

## Verification
Open the configured origin, visit Profile and choose Sign in. The page loads Google's own button only after this action. Check success, cancellation, expired attempt, sign-out and reload. No cloud-plan sync is implied. Visible pages renew valid sessions near expiry, up to 12 hours from Google authentication. Inactivity beyond 15 minutes requires another sign-in. Also verify account deletion requires fresh sign-in and explicit reconfirmation; use a disposable test account. Android client registration is covered below.

## Android OAuth client (Phase 1)

Android is the primary pilot client, and real sign-in on physical phones is a
Phase 1 gate. The native app uses Google Credential Manager (One Tap) and asks for
an ID token for the **Web** client above; Google only issues it to an app whose
package name and signing certificate are registered as an Android OAuth client in
the same project. No client secret is involved.

Values from the repository:

- Package name: `com.routiqo.app` (`apps/mobile/app.json`, `android.package`).
- App environment: `EXPO_PUBLIC_ROUTIQO_GOOGLE_WEB_CLIENT_ID` is the **Web**
  client ID (the server audience), not the Android client ID
  (`apps/mobile/.env.example`, `apps/mobile/src/auth/native-google.ts`). It must
  match `ROUTIQO_GOOGLE_CLIENT_ID` on the core API. `EXPO_PUBLIC_ROUTIQO_API_ORIGIN`
  is the HTTPS staging API origin.
- Core API profiles: `persistence,google-auth,native-auth`.

Steps:

1. In the same Google Cloud project, create an OAuth client of type **Android**
   with package name `com.routiqo.app` and the SHA-1 fingerprint of the signing
   certificate. Create one Android client per certificate:
   - **Debug:** the debug keystore used by the local development build
     (`<debug-keystore-path>`, typically generated by `expo prebuild` or the
     Android Gradle plugin). Read its SHA-1 with
     `keytool -list -v -keystore <debug-keystore-path> -alias androiddebugkey`
     or `./gradlew signingReport` in the generated `android/` project.
   - **Release / internal test build:** the owner's upload or release key
     (`<release-keystore-path>`, `<release-alias>`). If Google Play App Signing
     is used, also register the Play **app signing** certificate SHA-1 shown in
     Play Console, since installed Play builds are signed with that key.
2. Record each registered fingerprint as `<sha1-debug>`, `<sha1-release>` and
   (if applicable) `<sha1-play-app-signing>` in the operator notes, not in the
   repository. Fingerprints are not secrets, but keystores and passwords are:
   never commit a keystore or put its password in the repository, app bundle or a
   task message.
3. Keep the consent screen in testing mode with the pilot testers added, or
   publish it after review before the dry run.
4. Build with the Web client ID and staging API origin set, install on a physical
   phone and sign in. Verify success, cancellation, no saved credential (account
   creation path), renewal, sign-out, account switch and recent-auth deletion.
   Record results in `docs/validation/NATIVE_ANDROID_PENDING.md`.

Check during the first real Android sign-in: the core API verifier
(`GoogleTokenVerifier`) accepts an `azp` (authorized party) claim only when it is
absent or equal to the configured Web client ID. Google may set `azp` to the
Android client ID for tokens issued to an Android app. If real Android tokens are
rejected for that reason, record it in the ledger; accepting the Android client ID
as an authorized party is a reviewed code change, not a configuration workaround.

References checked: https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid and https://developers.google.com/identity/gsi/web/reference/js-reference .
