# Public LIVE privacy protocol — implementation contract

This is the ADR 0053/0054 person-level DP candidate only; further research is paused and its existing code/docs remain preserved. [ADR 0055](../../adr/0055-consented-community-traffic-summary-proposal.md) authorizes implementation and staging evaluation of a separate consented community-summary contract that does **not** satisfy this protocol or inherit its privacy claim. The owner has not accepted that change for production; neither path permits production traveller output today.

Status: **user-selected implementation direction, independent protocol review pending; public output disabled**. ADR 0051's mutable suppression and ADR 0052's delayed decision were rejected. ADR 0053 supplies a candidate person-level noise mechanism, not a complete release protocol. ADR 0054 specifies immediate Share as the proposed input boundary. No existing receipt, intent, person claim or private evaluator is a publishable Live Moment.

## Protected fact and scope

- Protect whether one independently verified person added one public traffic report to the finite 30-day pilot. Neighboring pilot datasets differ by adding or removing that person's entire public input. A change of report key is a two-step replacement with a separately stated composed bound. This is a bound on the **whole public release transcript**, not a promise that no one can infer participation from outside information or the person's own disclosures.
- Freeze before the pilot starts its 30-day interval, versioned Chennai/OMR catalog of at most ten coarse anchors, traffic category, four allowed values, nonoverlapping five-minute windows, release/expiry schedule, and maximum 345,600 public keys. An account, caller, provider response or observed report cannot add a key or change this manifest mid-pilot. A later pilot needs a separate privacy-budget and product decision.
- A person may affect at most one public key in the entire pilot, across accounts, journeys, retries, windows, anchors and values. The same stable person reference must survive account deletion and re-verification through the retention horizon. V17's one-active-account index and V21's disconnected claim do not yet enforce this end to end. Google sign-in, route binding and client GPS do not prove independent people or physical presence.

## Explicit Share and Stop

- An eligible person deliberately selects one current private Quick Signal after a purpose-specific disclosure. The server checks current owned journey, consent, recent receipt, context/catalog, verification, restriction and abuse authority before accepting. **Successful Share atomically consumes the person's pilot slot and freezes only the canonical public key as irreversible pilot input.** An exact retry returns that committed outcome; a second or changed request cannot consume another slot. An uncertain client result must be resolved from owner-only durable state before any claim of success or failure.
- Stop, Ghost Mode, journey completion, account deletion, verification revocation and moderator restriction prevent future Share attempts. If they serialize **before** the Share transaction, no input is frozen. If Share commits first, they cannot retract that pilot input or change a later aggregate. A success response must say this plainly. `Stop public consideration` and a `stopped` response cannot imply removal of an already frozen input. Existing V18 ACTIVE/STOPPED intents, deletion cascades, browser copy and the immediate-suppression wording are incompatible with this protocol and must be changed before activation.
- Frozen input is a traffic-category claim from a verified contributor at Share time, not a continuing assertion of presence or a safety guarantee. Published rows never identify an individual. The public input and nonrefundable person claim need a bounded, reviewed retention and deletion exception; a private signal receipt and account history retain their existing independent lifetimes. No raw identity document, account ID, exact coordinate, endpoint or movement history enters the public input table.

## Fixed randomized release

- Use ADR 0053's candidate observed-key sparse geometric histogram: for every precommitted key draw two independent capped 64-bit geometric values, including absent keys; emit an **observed** key only when its count plus noise reaches 22. Emit a coarse condition for an anchor/window only if exactly one traffic value survives; zero or multiple survivors produce no condition. This selection uses only the released-key set and frozen manifest, never original counts. Counts, confidence, support floor, member lists, individual timestamps and precise positions are never output. A singleton can exceptionally pass the threshold, and the output may be wrong; do not describe a row as confirmed or safe.
- The candidate add/remove person-level bound for the **entire pilot** is `(epsilon = ln 2, delta <= 1/3,145,728 + 3K * 2^-63)` for fixed `K <= 345,600`, only if all input bounding, noise, transcript and failure assumptions hold. The claim, proof and implementation require independent specialist review. An observed-only key and its existence/absence are part of the mechanism. No unnoised side channel may reveal whether that key has support.
- Publish each closed window only at its precommitted release boundary and expire it at its precommitted expiry. Materialize one durable terminal decision, including empty output, across replicas; retries never redraw noise or change bytes. Public response status, timing, cache state, moment reference, order and expiry must be fixed functions of the manifest and the frozen randomized result. A late job, unavailable dependency or incident cannot produce a source-dependent appearance, disappearance or special denial. The implementation must demonstrate bounded worst-case work or a reviewed source-independent global fail-closed mode before release.
- Every reader of a canonical moment sees the same bytes. Reads require current owned active journey and relevant server-derived context, with shared rate controls. No caller-selected anchor, coordinates, area, time window, member filter or per-viewer subtraction. Block policy may deny a reader the entire traveller feed, but must not alter a canonical row or reveal which person contributed. Official alerts remain separately labeled and unaffected.
- A source action after Share or publication cannot edit, suppress or withdraw a public aggregate. Viewer-side Ghost Mode, account change or journey completion clears that viewer's in-memory rows; previously delivered copies elsewhere cannot be recalled. The product disclosure and deletion policy must explicitly state this limit. A source-specific exceptional takedown or moderation action is outside the proposed guarantee and blocks activation until a reviewed, source-independent response is defined.

## Complete observable transcript and review

The review must include every public observation across the pilot: row existence and absence, value, area/category/window label, canonical reference, ordering, response size/status/latency, first visibility, expiry, retries, rate-limit behavior, error and emergency modes, caches, offline copies and repeated reads by colluding accounts. It must also examine whether private Share/Stop or verification behavior can be observed by a different person. No public signal endpoint or flag may be enabled from a mathematical sampler test alone.

Adversarial evidence must cover known-neighbor and colluding verified people; deletion and re-verification; Share racing Stop, Ghost Mode, completion, restriction and expiry; repeated/adjacent keys; data-dependent deadline misses; outages, restarts and multi-replica retries; block toggles; stale clients; and false or conflicting traffic reports. Review the actual implementation and generated output, not only the ADR. Record the review disposition and findings in `docs/validation/PUBLIC_LIVE_PENDING.md`.

## Release gates

1. Independent mathematical, privacy and security review accepts the complete ADR 0054 protocol, explicit neighboring relation, bounded contribution, sampler implementation and observable transcript. Critical/High findings block release.
2. Product and privacy review accepts irreversible Share copy, Stop/Ghost/deletion semantics, retention and the accuracy limits. Current browser and API wording must be replaced and tested before the Share flag can turn on.
3. Durable frozen-input transaction, stable person assignment, fixed manifest, canonical publisher/reader, reporting and moderation operations pass concurrency, abuse, staging, load and device tests. The disconnected V19 evaluator must never back public reads.
4. Real consented density and accuracy measurements establish that the threshold-22 mechanism gives useful, truthful-enough traffic information. With ten or twelve agreeing reports, publication is exceptionally rare; no synthetic fixture can close this gate.

Until all gates close, traveller-derived public LIVE remains disabled. The separately default-off official-alert pilot is not approval for traveller publication.
