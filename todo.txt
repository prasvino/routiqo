ROUTIQO — CURRENT STATUS, REMAINING WORK AND COMPLETION REQUIREMENTS
Snapshot: 19 September 2026 (IST)
Repository snapshot: private journey consent controls following audited moderation in 312e599

CURRENT POSITION

Routiqo has a working local planning preview and substantial tested backend
foundations. It is not production-ready. An implemented API or disabled feature
is not the same as an integrated, deployed and verified user experience.

The agreed first release is an active-journey LIVE list with Live Moments and
Quick Signals, supported by Google sign-in and a reviewed regional maps pilot.
Full offline navigation, broad social features and AI belong to later phases.

2. WHAT IS REQUIRED TO COMPLETE THE PENDING WORK

A. Resolve public Live privacy and publication design
   ADR 0038 records why threshold-only publication is unsafe. Under an absolute
   deterministic single-person non-inference guarantee, useful output is not
   possible. Define and independently review a measurable privacy contract.
   This is a design gate, not a credential dependency.
   - Specify fixed geographic partitions and time windows, contribution
     eligibility, evidence independence, publication/suppression rules and
     distributed query budgets.
   - Resolve block, withdrawal, Ghost Mode, completion and deletion behavior
     without creating an oracle that reveals an individual's contribution.
   - Test coordinated accounts, repeated queries, neighboring anchors, threshold
     changes, stale caches and consent races. A minimum contributor count alone
     is not proof of privacy.
   - Record the decision in an ADR and complete independent privacy review.
   Complete when: a falsifiable, reviewed policy exists and adversarial tests
   pass. Public projections must remain closed until this gate is satisfied.

B. Finish abuse prevention, moderation and revocation
   Engineering can proceed alongside the privacy design.
   - DONE: rolling 20/hour actor budget and 60-second anchor/category cooldown,
     independent ledger, cleanup, replay and concurrent-limit tests.
   - DONE: durable private suspension and grant-revision fencing; unsuspending
     cannot restore previously issued unused grants.
   - Define and implement evidence eligibility/anti-Sybil safeguards.
   - Complete reporting reference authority: canonical evidence identity,
     exact retry after revocation, shared lock order and investigation after
     source expiry. The intake proposal is deliberately not implemented.
   - DONE internally: finite RESTRICT/RESTORE database permissions and atomic
     restriction/audit/debit commands with bounded retention (ADR 0041).
     No operator identity is authenticated or permission seeded by this slice.
   - Add strong admin authentication, controlled grant administration and
     case/target scope. Then connect durable reports and the operator queue.
   - Establish operator alerts, supervision, appeals and approved audit/backup
     retention; activate and verify bounded moderation cleanup in staging.
   - DONE: private directed block persistence, ordered account-pair locks,
     bounded retained revisions and tested concurrent/deletion behavior.
   - Connect private blocking to safe authorized public targets and delivery;
     internal bilateral snapshots do not authorize later publication.
   - Enforce policy changes across reads, derived data and any future delivery
     channels; fail closed when authority is unavailable.
   Complete when: multi-user, concurrent, replay, abuse and revocation tests
   pass and an operator can handle a report through a documented process.

C. Build the first LIVE user experience
   Depends on A and B for real public output.
   - DONE: typed private browser consent/context/Quick Signal clients, strict
     runtime validation, exact revisions, bounded deadlines and cancellation.
     Private consent and explicit route preparation are mounted for confirmed
     active journeys; there is no public LIVE interface. Browser auth and routing
     transports also bound streamed JSON and refuse redirects.
   - DONE internally: optional validated curated route-area labels, preserving
     old unlabeled catalogs and existing API/resolver outputs (ADR 0042).
   - DONE internally: authority-scoped read-only choice snapshots with current
     consent, restriction, provenance and expiry checks (ADR 0043); no endpoint.
   - Add a guarded owner choice API/client and exact displayed-context issuance
     semantics before Quick Signal controls.
   - Connect Quick Signal actions to the active owned journey. Preserve
     Home/Explore/Trips/Profile navigation and explicit grant/receipt recovery.
   - Implement authorized Live Moment reads and a bounded foreground refresh
     flow, with cancellation, backoff and one request in flight.
   - Show truthful freshness/conflict/suppression states; never invent reports,
     report counts, live participants or verified physical presence.
   - Keep visible offline Live rows in memory, mark stale, remove expired rows
     and disable submission. Clear on local Ghost/account/journey transitions.
   - Reauthorize on reconnect; never upload an old report automatically as a
     fresh observation. Handle uncertain writes with exact explicit retries.
   Complete when: authenticated end-to-end, offline, account-switch, expiry,
   revocation, accessibility and small-screen acceptance pass.

D. Configure and verify real Google sign-in
   Requires account-owner configuration; implementation alone cannot supply it.
   - Configure the Google project, OAuth client/audience, consent screen and
     approved origins/redirects for the intended environments.
   - Supply credentials through local/deployment secret configuration, never
     chat, source control or public client bundles.
   - Verify real sign-in, renewal, logout, expired sessions and recent-auth
     account deletion through the deployed browser/proxy boundary.
   Complete when: real accounts pass the intended login/lifecycle flow in staging.
   Phone OTP remains deferred; Google is the agreed first method.

E. Provision the open-source regional maps pilot
   Requires reviewed data and operator-controlled infrastructure.
   - Select the pilot region/corridor and review dataset coverage, provenance,
     licenses, update cadence, disk capacity and import requirements.
   - Provision controlled Valhalla, Photon and tile hosting (Martin direction),
     including MapLibre style, sprite and glyph resources.
   - Configure fixed service origins and conservative geographic bounds; protect
     internal services and redact query/body logs across proxies/providers.
   - Build a reviewed versioned anchor/category catalog for Live route binding.
   - Test real routes, alternatives, search, attribution, outages, coverage
     failures, network/egress behavior and regional data updates.
   Complete when: the selected pilot works against real controlled services and
   the catalog/endpoint-exclusion privacy review passes. Mapbox tokens are not
   required for the selected direction. Artifact checks alone are insufficient.

F. Finish journey/offline reliability and verify existing features
   - Exercise multiple devices/accounts, delayed responses, duplicate commands,
     network flaps, interrupted writes, unavailable storage and unresolved
     conflicts. Preserve account retirement and exact replay semantics.
   - Complete broader restoration without silently overwriting local pending work.
   - Verify journal conflicts, navigation protection, older account history,
     summary completeness disclosures and backup/restore with real sign-in.
   Complete when: data survives the supported failure/recovery flows without
   cross-account exposure, duplicate completion or lost acknowledged work.

G. Complete native Android integration
   Required for Android launch; can run alongside the web pilot work.
   - Implement redirect-safe native authenticated transport, Google challenge
     binding/UI, secure-vault coordination and logout/deletion integration.
   - Mount authenticated journey operations and native reconnect dispatch.
   - Integrate MapLibre in a development build and verify platform permissions.
   - Run scripts/android-doctor.ps1 to establish CURRENT machine readiness.
     Last recorded prerequisites included SDK API 36, Build Tools 36.0.0,
     Platform Tools, Command-line Tools, Android JDK 17 and an emulator/device.
     Backend uses JDK 25 separately. Do not assume earlier missing tools remain
     missing; this report did not rerun the machine inspection.
   - Verify SQLite/SecureStore restart, account isolation, backup behavior,
     location denial, accessibility, performance and unreliable networks on device.
   Complete when: a signed release candidate passes real-device QA. JavaScript
   export or a successful compile is not device verification.

H. Operate retention and prepare deployment
   Requires an agreed hosting environment and operator access.
   - Configure production PostgreSQL/PostGIS, required cache services, secrets,
     networking, TLS/domain, runtime profiles and separately gated features.
   - Validate migrations in staging, backups/restores and rollback procedures.
   - Enable expiry maintenance only after retention/backlog tests; measure the
     intended replica count, monitor failures and define cleanup capacity alerts.
   - Establish redacted monitoring, health checks, incident ownership, privacy
     disclosures, deletion/backup policies and minimum moderation operations.
   - Run remote CI on the actual release commit; perform authenticated release,
     load/capacity and deployment smoke tests before gradual pilot rollout.
   Complete when: staging acceptance and operational runbooks are verified, then
   the release is deployed and checked. Current work has not deployed production.

I. Later navigation and product expansion
   These do not block the agreed first LIVE list.
   - Offline maps/navigation: define storage limits, download/update integrity,
     eviction/account-deletion behavior, permission/GPS handling, guidance and
     on-device rerouting; validate supported device/region performance.
   - Map LIVE overlay: reuse the same authorized projection without adding a
     finer-grained location/query surface.
   - Ask Ahead/rooms/realtime: separate recipient-consent, anti-targeting,
     membership-expiry, blocking, moderation and reconnect/revocation design.
   - Push/reminders/media/AI: provider setup, permission/retention controls,
     bounded jobs/uploads, signed media flow, fallbacks and feature-specific QA.
   - Pulse/Travel Waves: establish useful evidence and participation first.
   Complete when: each separately scoped feature meets its own reviewed spec;
   these must not inflate the first-release checklist.

3. RECOMMENDED EXECUTION ORDER

1) In parallel: publication/privacy design (A), abuse/moderation foundations (B),
   real OAuth setup (D) and regional maps/catalog provisioning (E).
2) Implement the approved public projection, then integrate the LIVE list and
   contribution experience (C). Continue journey/offline verification (F).
3) Complete staging operations/retention and pilot acceptance (H).
4) Launch the reviewed web pilot after all first-release gates pass. If the
   initial launch includes Android, native integration/device QA (G) also blocks it.
5) Expand native navigation and later product features (I) in separate phases.

Engineering can continue now on design, abuse controls, moderation, native
transport and tests. Real OAuth, live regional data/services, deployment access
and device verification remain external/configuration-dependent work. No new
software installation is required merely to continue the existing backend work.
